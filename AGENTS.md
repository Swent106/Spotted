# AGENTS.md

Durable rules for any AI agent working in this repository. Read this before acting.

## The app

A Kotlin/Android app (`com.android.spotted`) built with an **MVVM** architecture.

- `model/` holds data classes and repository **interfaces**.
- `data/` holds repository implementations (Firestore, Storage, Auth, Location, ...).
- `ui/` holds screens and their **ViewModels**.
- Repository implementations are wired into ViewModels by each ViewModel's
  `companion object { val Factory }` (see [ViewModel](#viewmodel)).

## Plan before you change anything

Before editing any file, explain your plan in plain English and wait for approval.
Do not show diffs, create files, or run commands that modify the repo until the
user explicitly approves (e.g. "go", "approved", "yes").

The plan must include:
- **Goal**: one or two sentences on what you're trying to achieve.
- **Changes**: each file you will touch, and what you will change in it and why.
- **Not touching**: anything nearby you will deliberately leave alone.
- **Risks / questions**: anything uncertain, or any decision the user should make.

Keep it short: a reader should understand it in under a minute. No code in the
plan unless a signature or interface change needs to be shown.

Once approved:
- Change only what the plan describes. If you discover you need to touch another
  file or do something different, stop, explain why, and wait for approval again.
- After the changes, summarize in plain English what you did, and call out
  anything that differs from the approved plan.

## Architecture (MVVM)

### Layers and packages
- `ui/<feature>/`: `<Feature>Screen.kt` (View) and `<Feature>ViewModel.kt`
- `model/`: data classes (Pet, Alert, UserProfile...) and repository interfaces
- `data/`: repository implementations (Firestore, Storage, Auth) and fakes for tests
- Dependencies point one way: View → ViewModel → Repository interface → implementation.

### Model / data layer
- Every data source is accessed through a repository **interface** in `model/`.
- Implementations live in `data/`. Each interface has a `Fake...Repository` for tests.
- Repositories return `Result<T>`. They never throw to the ViewModel.
- Repositories are main-safe: blocking I/O runs in `withContext(Dispatchers.IO)`.
- IDs are generated by the repository (`getNewId()`), never by the UI.
- No Firebase types (`Timestamp`, `FirebaseUser`, `DocumentSnapshot`) outside `data/`.
  Use plain Kotlin types (e.g. epoch millis for dates).

### ViewModel
- **Never imports Firebase, Android `Context`, or any Composable.**
- Gets its dependencies through the **constructor**, as interfaces. Provides a
  `companion object { val Factory }` for production; tests call the constructor directly.
- Exposes exactly one `StateFlow<<Feature>UiState>`, backed by a private
  `MutableStateFlow`. Only the ViewModel modifies it.
- `UiState` is an immutable data class. Derived flags (`canSave`, `canPublish`) are
  computed properties of the state.
- Business rules live here (required fields, permissions, "already exists"...).
- Navigation is signalled through state (`destination`, `saved`, `done`); the View performs it.
- Async work runs in `viewModelScope.launch`. **Never `runBlocking`.**
- Time comes from an injected `now: () -> Long`, not from `System.currentTimeMillis()` directly.

### View (Compose)
- Each screen has two parts:
  - `<Feature>Screen(vm)`: a thin wrapper that collects state and handles navigation;
  - `<Feature>Content(state, on...)`: stateless, and the part UI tests target.
- Views contain no business logic and no repository calls.
- Only format checks happen in the View (email shape, phone digits).
- Every interactive or asserted element has a `Modifier.testTag("<feature>_<element>")`.
- System UI (Credential Manager, Photo Picker, permissions) is launched from the View;
  results are passed to the ViewModel as plain values.

## Tests

This project has two test source sets:

- `app/src/test/`: local unit tests. Run on the JVM, no device needed.
  Command: `./gradlew testDebugUnitTest`
- `app/src/androidTest/`: instrumented tests (integration and E2E). Need a
  running Android emulator or device, and the Firebase emulator.
  Command: `./gradlew connectedDebugAndroidTest`

When to run them:

1. **Before changing anything**, run the unit tests and note any failures. This
   is the baseline, so pre-existing failures are not blamed on your change.
2. **While working**, run the unit tests after each meaningful change.
3. **Before saying the task is done**, run both suites:
  - `./gradlew check` (unit tests + lint) and `./gradlew ktfmtCheck`
  - `./gradlew connectedDebugAndroidTest`, but first check `adb devices`.
    If no device is listed, do not skip silently: say that instrumented tests
    were not run and why.

Reporting:

- Report the results of both suites in plain English: what passed, what failed,
  and what could not be run.
- Clearly separate **new failures** (caused by your change) from **failures
  already present in the baseline**.
- If a test fails, explain the likely cause and propose a fix, but do not change
  the test or the code under test to make it pass without approval.


## Definition of done

- The change meets its acceptance criteria.
- `./gradlew check` (unit tests + lint) and `./gradlew ktfmtCheck` pass.
- The relevant higher-level tests (see table) pass, or you have reported that
  you could not run them.

## How to work

- One bounded, reviewable change per PR. If it sprawls across unrelated files,
  split it.
- Stage only the files you changed; never `git add .` or `git add -A`.
- Commit with a Conventional Commit subject of at most 50 characters
  (e.g. `feat(auth): add user sign-in`), and a body wrapped at 72 characters
  when needed. End the message with a `Co-authored-by:` trailer crediting the
  AI agent.
- **Acknowledge AI in every source file** you create or substantially edit, with a
  comment at the top of the file, e.g.
  `// Portions of this code were generated with the help of Claude (Anthropic).`
  The course collaboration policy requires this in addition to the commit trailer;
  without it, the code counts as plagiarism. Keep existing acknowledgments and add yours.

## Responsibility

The human sets the goal, context, and acceptance criteria, reviews the diff, and
owns every line submitted. The agent's job is to make that review easy: small
diffs, clear commits, and an honest report of what was and wasn't verified.
## Git branches

- Never commit directly to `main`. All work goes through a PR.
- Use one branch per task. The standard format is
  `<type>/<issue-number>-<short-description>`, with a 2–5-word description.
- Use lowercase and hyphens. The type is one of:
  - `feature`: new feature or enhancement
  - `fix`: bug fix
  - `hotfix`: urgent production fix; still submit it through a PR
  - `docs`: documentation only
  - `refactor`: restructuring without behavior changes
  - `test`: adding or updating tests
  - `chore`: maintenance, dependencies, tooling, or CI
  - `release`: preparing a release
- Release branches are the exception to the issue-number format; use
  `release/<version>`, e.g. `release/v1.2.0`.
- Examples: `feature/42-report-lost-pet`, `fix/57-map-marker-offset`,
  `hotfix/63-login-crash`, `docs/12-update-wiki-home`,
  `refactor/30-split-pet-service`, `test/48-pet-search-endpoint`,
  `chore/21-upgrade-dependencies`
- Keep the branch up to date with `main` before opening a PR. Delete it after merging.

## Commit messages

Use this format:

    <type>[optional scope][!]: <lowercase imperative description>

    [optional body]

    [optional footer(s)]

- Use one logical change per commit. Keep the whole subject line to 50
  characters or fewer, use the imperative mood, and do not end it with a
  period.
- Valid types: `feat`, `fix`, `docs`, `style`, `refactor`, `perf`, `test`,
  `build`, `ci`, `chore`, and `revert`.
- Scope is optional and identifies the affected area, e.g.
  `feat(report): add lost pet form`.
- Use a body when it helps explain what changed and why; wrap it at 72
  characters. Keep commit messages in English.
- Add an issue reference footer when relevant, such as `Closes #12` or
  `Refs #12`.
- Mark breaking changes with `!` before the colon or a `BREAKING CHANGE:`
  footer.
- Include the required `Co-authored-by:` trailer crediting the AI agent.

Example:

    fix(map): correct marker offset on zoom

    The marker position was computed before the map finished loading,
    which shifted it on high zoom levels. Compute it after the load event.

    Closes #57

    Co-authored-by: Copilot <223556219+Copilot@users.noreply.github.com>
